# E-commerce implementation progress

## Phase 1 — Authentication and authorization

- Existing session authentication is reused.
- Order administration endpoints require `ADMIN`; customer order endpoints require `CUSTOMER`.
- Public customer registration remains unavailable in the existing application.

## Phase 2 — Persistent cart and checkout

- Cart contents now persist in the existing PostgreSQL `carts` and `cart_items` tables; no schema migration was needed.
- Guest carts are keyed by a server-generated random token in an HttpOnly, SameSite=Lax cookie; only its SHA-256 digest is stored in the database. Customer carts are resolved from the authenticated server principal, never from a browser-supplied user ID.
- The cart API supports retrieval, add, quantity update, item removal, and clear. The server validates active product/offer status, stock, quantity limits, stored currency, and stored price; it returns offer IDs without internal offer codes and calculates subtotals from database prices.
- Guest carts merge transactionally into the authenticated customer's cart at login. Duplicate offers add quantities only when the combined quantity is within the current stock and quantity limit. Failed merges retain the guest cart and report the conflict. Successful checkout removes purchased lines from the customer's active cart in the same database transaction.
- The storefront product page, cart, and checkout now use the backend cart API rather than browser-local cart storage. The cart shows loading, empty, success, error, availability, quantity, unit-price, and subtotal states; checkout still revalidates all prices and stock.
- Guest checkout now uses the persisted guest cart and backend checkout pricing/inventory path; implementation and remaining verification are recorded in Phase 12.
- No shipping-rate or coupon rules exist in the current project; checkout records zero shipping fee and zero discount rather than inventing rates or coupons.

## Phase 3 — Orders and simulated payments

- Customer and Admin order APIs read persisted orders. Checkout creates orders with item/price/currency snapshots and inventory-reservation records.
- Customer-owned orders using `SIMULATED_ONLINE` can run a persisted, idempotency-keyed payment attempt. Provider outcomes are configured by `orders.simulated-payment.outcome` (`SUCCEEDED`, `FAILED`, `PENDING`, or `CANCELLED`).
- No payment outcome advances fulfillment status.
- Payment status remains separate from fulfillment status.

## Phase 4 — Customer order screens

- Customer order history and detail now load persisted orders and status history.
- Customers can submit cancellation requests for orders not yet shipping.
- DEMO offer lines and unverified financial totals are withheld from customer views.
- No live tracking link, delivery estimate, or carrier integration is presented.

## Phase 5 — Admin order management

- Added PostgreSQL endpoints and UI for manual fulfillment updates, cancellation approval/rejection, and carrier/tracking edits.
- Status changes store previous/new state, timestamp, actor identity/role, action, and note.
- Allowed fulfillment transitions are explicit; no elapsed-time status automation is used.
- Cancellation approval releases only recorded active reservations. Paid orders receive a persisted simulated refund record when a single order currency can be established.
- Admins can retry failed simulated refunds. Attempts are persisted with an idempotency key; repeated keys do not call the gateway again, and pending or successful refunds cannot be retried. Unit tests cover retry persistence and duplicate-refund guards.
- Inventory is consumed only for recorded active reservations when an order moves to Shipping; legacy orders without reservation records are not adjusted automatically.
